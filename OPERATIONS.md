# APT publication operations

The public endpoint is https://projectcuriositas.github.io/apt/, suite stable,
component main, architecture amd64. Ubuntu 24.04 and 26.04 are the initial targets.
Python 3.12+, GnuPG, apt-utils and dpkg-dev are required to build the site.

## Bootstrap state

An empty releases list builds a preparation page only. It requires no signing
secret and publishes no unsigned or test-key repository. Install commands appear
only after the production key and approved release inputs pass all checks.

## Publish a release

1. Complete the offline key ceremony and register the APT-only environment
   secrets described in KEYS.md. Review the public key and full fingerprints.
2. Publish the formally authorized Mognitio release with its immutable tag,
   signed manifest.json / manifest.json.asc and Debian package asset.
3. In a feature branch, append a repository.json release record with version,
   tag, exact tag commit, manifest_sha256, deb_sha256 and deb_size.
   All values must come from the frozen release artifacts. The package name is
   mognitio_VERSION-1_amd64.deb. A Debian revision change requires an explicit
   extension of this registry contract; never replace existing bytes.
4. Review and squash merge the pull request. The main-branch Pages workflow
   downloads the exact public release, checks tag and manifest identity, verifies
   the bundle subkey signature and package hash/control fields, then signs the
   full APT tree using its separate subkey. No compiler or package build occurs
   in the signing job.
5. The deploy job uploads only the fully verified public site. It has no
   signing secrets. Verify HTTPS InRelease, keyring, apt update, apt download,
   install/run/build/test/LSP/remove on both supported clean OS environments.

Failures in verification or signing prevent deployment; the previous published
tree remains available. Package versions are immutable and retained in the registry.
Concurrent publications are serialized. Do not bypass failed validation.

## Metadata renewal

The workflow runs weekly and can be dispatched manually. It reuses the reviewed
immutable release registry and signs new metadata with a 14-day Valid-Until.
Monitor failed workflow runs and renew before expiration. Users must not disable
APT signature or expiry checks to work around an outage.

The release-signing environment accepts only main deployments. Pull requests
run validation without production secrets. GitHub actions are pinned to commits;
review pin updates through pull requests.

## Initial trust and revocation

Initially, the reviewed GitHub repository and its Pages site publish the public
key and full fingerprint. Both are controlled by the same GitHub account; they
are not independent trust channels. An independent official channel is deferred.
A GitHub account compromise therefore requires an out-of-band identity recovery
before trusting a replacement key. Do not describe the initial setup as resistant
to compromise of its hosting account.

Production trust setup is not complete until the actual public fingerprints are
reviewed and committed. No production key is generated by the Pages build.

gpgv signature success is not a guarantee of current revocation knowledge.
Refresh the repository-specific public key and revocation information before
offline bundle verification. Never trust a key merely because it accompanies
an archive. Keep primary keys and revocation backups offline.

On compromise, disable the signing workflow and remove the affected environment
secret. Use the offline primary to revoke/replace the signing subkey, publish
updated public trust information, and verify both supported APT clients before
resuming. A stale offline keyring cannot detect subsequently published revocation.
